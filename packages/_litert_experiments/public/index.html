LiteRT.js experiments

Browser experiments for running one shard of a language model with LiteRT.js on WebGPU, for issue #179, which is the implementation plan of issue #178.

  • LiteRT.js WebGPU gate — milestone zero. Does @litertjs/core load a .tflite graph and compile it for WebGPU at all?
  • LiteRT.js key/value cache residency gate — milestone one. Can a shard's own key/value cache stay resident on the graphics processor between repeated model.run() calls?
  • LiteRT.js multiple output diagnosis — part of milestone one. Names which graph shape WebGPU computes wrongly, one property at a time.
  • Qwen3-0.6B LiteRT.js shards — milestone two. Every real .tflite graph of Qwen3-0.6B, and the whole model chained, checked element by element against PyTorch.
  • Resident key/value cache over a real decode — the de-risking gate of milestone four. Does a real decoder shard's key/value cache survive staying on the graphics processor across a whole sequence of decode steps?
  • Prefill at fixed prompt lengths — milestone five. One exported signature per prompt length, and what reading a whole prompt in one call is worth against reading it one token at a time.
  • Both runtimes in one page, alternating — milestone six, done properly. The same page gave anything from 7 to 25 tokens per second on different loads, so the two runtimes are run alternately inside one load instead, where the ratio between them survives whatever the machine is doing.
  • The comparison against ONNX Runtime Web — milestone six. The same model and the same prompt through the other runtime, so that the two can be put in one table. The two sides do not hold the same weights, and this page reads that difference off the running sessions before it measures anything.
  • Qwen3-0.6B across browser workers — milestone four. Generating tokens with the shards spread across separate browser pages, each keeping its own key/value caches, with only the hidden state crossing between them.
