Resident key/value cache over a real decode

The de-risking gate of milestone four of issue #179. Milestone one showed that a tensor can stay on the graphics processor between model.run() calls, but it showed it with a graph holding one matrix multiplication and an addition. Milestone two ran a real Qwen3-0.6B decoder shard, but only for a single step, at one position, with an all-zero cache.

This page asks the question those two leave open: does a real decoder shard's key/value cache survive being kept on the graphics processor across a whole sequence of decode steps? Each step feeds the cache tensor that came out of model.run() straight back in as the next step's cache input, so the cache is never read into JavaScript at all.

One shard is enough to answer it, and one shard is all this page loads. Decoder shard decoder_00-03 takes the embedding row of the token at each position, so its inputs for a whole sequence are known in advance and no other shard has to run. Every step's output hidden state is compared against PyTorch running the same shard over the same tokens.

The same loop then runs a second time with the cache read back into JavaScript and uploaded again on every step. That variant is the control: it says both whether keeping the cache resident changes the answer, and what keeping it resident saves.

Reads its shard and its reference from /qwen3-litert-shards/models, which tools/qwen3_litert_shard_export/ and tools/qwen3_decode_reference/ write.
