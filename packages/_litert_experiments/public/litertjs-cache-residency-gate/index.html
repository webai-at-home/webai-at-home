LiteRT.js key/value cache residency gate

Milestone one of issue #179, and the milestone the whole investigation turns on. It asks whether a shard's own key/value cache can stay resident on the graphics processor between repeated model.run() calls, instead of being copied out to JavaScript and back on every generated token.

The graph is not a transformer. It has the shape of one decoding step of one shard: a hidden state and a key/value cache in, a new hidden state and an updated cache out. The hidden state is the tensor that has to leave the graphics processor, because the next shard is on another device. The cache is the tensor that must never leave it.

Three loops run, differing only in what leaves the graphics processor on each step:

  • resident-with-hidden-readback — the cache stays put and only the hidden state is read back. This is the distributed decode this project wants.
  • resident-without-readback — nothing is read back. The upper bound of what residency can buy.
  • cache-round-trip — the whole cache is read out and uploaded again every step. The naive design issue #178 warns against.

The graph is a generated artifact and is not committed. Write it first with tools/cache_residency_export/export_shard_like_step.py.
