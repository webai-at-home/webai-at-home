# Directory Context: `/packages/webai_at_home_cli`

## Purpose

The single command line program published to the npm registry as `webai-at-home`, so a user runs `npx webai-at-home <command>` without cloning this repository. It dispatches to the other four command line programs in this repository — `@webai/gateway`, `@webai/consumer-openai`, `@webai/worker-openai`, and `@webai/consumer-cli` — rather than reimplementing any of them. See [issue #170](https://github.com/webai-at-home/webai-at-home/issues/170).

## Key Exports & Entry Points

- `src/cli.ts`: the command line program, `Cli`. `gateway`, `consumer_openai` and `worker_openai` each name one of the other three command line programs and run it, unchanged, on whatever follows, and `donate` and `serve` name `worker_openai` and `consumer_openai server` again by what a person is trying to do. Any other first word — a `consumer_cli` subcommand such as `submit`, or a global option such as `--gateway-url` written ahead of one — is handed whole to `@webai/consumer-cli`.
- `scripts/vendor_wrapped_programs.ts`: run by `prepack`, right after `npm run build`. Copies the built `dist` (and, for `@webai/gateway`, `web/dist`) of every wrapped program, plus a copy of `@webai/protocol` and, where needed, `@webai/consumer-cli`, into this package's own `dist/vendor`, then rewrites the four package-name imports in the freshly compiled `dist/cli.js` into relative paths pointing at that vendored copy. See that file's own comment for why a plain copy replaced npm's own `bundledDependencies` mechanism.

## Local Rules & Boundaries

- Every one of the four wrapped programs takes the name it was invoked under as a parameter — `Cli.run(args, programName)`, and `new GatewaySettings(argv, programName)` and `new ServerSettings(argv, programName)` for the two that read their options through a settings class. This program passes `webai-at-home gateway`, `webai-at-home submit`, and so on, so no usage line names a program the person never typed. Run on their own the four keep their own names, which is what each parameter defaults to. Before this, the gateway and the OpenAI-compatible server both printed `Usage: program [options]`, because each built its parser with a nameless `new Command()`. See [issue #171](https://github.com/webai-at-home/webai-at-home/issues/171).
- The list of `@webai/consumer-cli` commands in the top-level help is generated by calling `ConsumerCliCli.buildProgram()` and reading back each command's own name and description, never hand-written here. The hand-written copy this replaced had already drifted from what those commands really say.
- `-V/--version` and `-h/--help` are both answered inside `Cli.run`, before the first word is matched, rather than being left to the built program alone: a first word this program does not recognise is handed to `@webai/consumer-cli`, which would answer either one with `error: unknown option`.

- Which of the four programs runs is decided by looking at the first word of the command line alone, in plain code, rather than by letting commander itself decide between a matching subcommand and a fall-through to `consumer_cli`. Commander's own handling of an option it does not recognise before a subcommand name, tried live, reached its own help text instead of the intended subcommand. See `Cli.run`'s own comment for what was tried and why it was dropped.
- Each of the three named subcommands sets `helpOption(false)`, so `--help` passes through like any other option and reaches the wrapped program's own, more detailed help, rather than this program's generic one-line description of it.
- This program never declares its own version of an option one of the four wrapped programs already has — `--port`, `--url`, `--config_dir`, and so on. `allowUnknownOption` and `passThroughOptions` keep this program's own parser out of the way instead.
- Every test in `tests/index.test.ts` that exercises a real subcommand runs this program in its own process, with `node:child_process`, rather than calling `Cli.run` in the test process directly: commander's default `--help` handling calls `process.exit` in each of the four wrapped programs' own, separate command line parsers, none of which this program overrides, which would otherwise end the test process itself partway through the first test that asked for `--help`.
- `@webai/consumer-cli`'s `Cli` is imported through its dedicated `./cli` subpath, not its default entry point, which deliberately does not export `Cli` — see that package's `src/index.ts`.
- None of `@webai/gateway`, `@webai/consumer-openai`, `@webai/worker-openai`, `@webai/consumer-cli`, or `@webai/protocol` is ever named in this package's own `package.json`, in `dependencies` or otherwise, even though a real install needs all five: naming a workspace member in `dependencies` makes `npm install <name>` and `npx <name>` resolve it against the real npm registry before ever looking at `bundledDependencies` — confirmed live on [issue #170](https://github.com/webai-at-home/webai-at-home/issues/170), a published `webai-at-home@0.1.0` that did exactly that 404'd trying to fetch `@webai/consumer-cli`, a package that has never been published on its own. `scripts/vendor_wrapped_programs.ts` copies the built files in directly instead, which Node's own module resolution finds on disk without ever consulting `package.json`'s `dependencies` field.
- This package's own `build`, and every one of the four wrapped programs' own `build`, run as part of `prepack`, so `npm pack` and `npm publish` never ship a stale or missing `dist`. Packing does not otherwise depend on having run `npm run build` by hand first.
- This package's own `version` no longer needs to match the five wrapped programs' own `version`, now that none of them is named in `package.json`: `scripts/vendor_wrapped_programs.ts` always copies whatever is currently built under `packages/*/dist`, regardless of what version number is written inside it.
